# Collaboration Conventions

**Load when:** adding a co-author, setting up a multi-author workflow, or any collaboration-related task.
**Skip when:** working solo on a project.

Multi-author workflows for academic research projects.

---

## Three-Location Model

A research project has two kinds of files: **code** (scripts, configuration, documentation) and **everything else** (data, materials, literature, outputs for the paper). These need different tools because git — the version control system we use for code — works poorly with large binary files and breaks entirely when placed inside a cloud-synced folder. Cloud sync services (Google Drive, Dropbox, OneDrive) write hidden metadata files into every folder they touch, which corrupts git's internal bookkeeping. This is not a theoretical risk — it has caused data loss in this workflow.

The solution is a strict separation: code lives in a local folder managed by git, shared data and materials live in a cloud folder that git never touches. We use two cloud services because they serve different purposes and one of them (Dropbox) is constrained by a third tool (Overleaf).

Every project therefore lives in exactly three places:

### 1. Local folder — code (git-tracked)

A folder on your machine that is **not** synced by any cloud service. This is where you clone the GitHub repository. All R scripts, configuration files, package management (`renv.lock`), project documentation (`CLAUDE.md`, `COAUTHOR_GUIDE.md`), and tracking files (`claude/` folder) live here.

When you run the analysis pipeline, it also generates intermediate and output files locally — cleaned data, tables, plots, serialized R objects. These are gitignored (never uploaded to GitHub) and never shared directly. Each author generates them independently by running the scripts.

**Why local, not cloud?** Git tracks every change to every file. Cloud sync services do the same thing, independently, at the same time. When both run on the same folder, they interfere with each other — cloud sync modifies files that git is in the middle of writing, or creates metadata files inside git's internal `.git/` directory. The result is corrupted repositories that cannot push, pull, or even read their own history. Keeping the git folder local avoids this entirely.

**What goes here:**
- All scripts (R, Python, shell)
- `renv.lock`, `.Rprofile`, `renv/activate.R`, `renv/settings.json`
- `.gitignore`, `CLAUDE.md`, `COAUTHOR_GUIDE.md`
- `claude/` folder (open issues, next steps, discussion files, pipeline map)
- `literature/*.md` summaries (the text summaries of papers, not the PDFs themselves)

**Also here but gitignored (generated by the pipeline, not shared):**
- `2_interim_data_steps/`, `3_clean_data/`, `7_r_objects/` — intermediate pipeline outputs
- `5_tables/`, `6_plots/` — generated outputs (synced to Dropbox for the paper, see below)

**Does NOT exist here:**
- `1_raw_data/`, `8_raw_data_backup/` — scripts read raw data directly from Google Drive
- Literature PDFs, experimental materials, codebooks — these live on Google Drive

**Setup:** clone via SSH (`git clone git@github.com:...`, requires SSH keys on GitHub) or HTTPS (`git clone https://github.com/...`, no keys needed). Document the recommended local path in `COAUTHOR_GUIDE.md`.

### 2. Google Drive — shared data and materials

All shared input files that are not code. One author creates the project folder on Google Drive and shares it with co-authors. This is the primary shared storage for everything that the scripts need to read but that should not be in git.

**Why Google Drive specifically?** It has the largest free tier (15 GB), which is more than enough for survey data, materials, and literature. We cannot use it for Overleaf (which requires Dropbox), so we use it for everything else instead of splitting across services arbitrarily.

**Folder template:**

```
<project-name>/
  data/
    study1/
      raw/            ← raw CSVs, Excel files (read by scripts)
      codebooks/      ← variable descriptions, data dictionaries
    study2/           ← when the project has multiple studies
  materials/          ← experimental stimuli, survey instruments, instructions
  literature/         ← PDFs of papers (text summaries go in git as .md)
```

Scripts access this folder via a path defined in `config_local.R` (see below). The folder path differs between machines and operating systems, so it is never hardcoded in scripts.

### 3. Dropbox — Overleaf sync only

Used exclusively to connect the analysis pipeline to the paper draft on Overleaf. Overleaf's sync feature only works with Dropbox (not Google Drive), so Dropbox is reserved for this single purpose.

One author owns the Overleaf ↔ Dropbox link (requires Overleaf Premium with Dropbox sync enabled in the Overleaf project settings). That author shares the Dropbox subfolder (`Apps/Overleaf/<project-name>/`) with co-authors.

All authors can push generated tables and plots into the paper: `sync_to_dropbox()` writes output files to the shared Dropbox folder on their machine → Dropbox syncs the files to the owner's machine → Overleaf detects the changes and updates the paper automatically. The owner's PC must be on with Dropbox running for the final sync step to work.

Document who owns the Overleaf connection in the project `CLAUDE.md`.

### Connecting the three locations: `config_local.R`

Since the cloud folders live at different paths on each author's machine (and may differ between Windows, Mac, and Linux), every project has a `config_local.R` file that maps the machine-specific paths. This file is gitignored — it is never committed or shared. Each author creates their own copy.

`config_local.R` defines at minimum:

```r
gdrive_project_path  <- "C:/Users/yourname/Google Drive/Research/<project-name>"
dropbox_project_path <- "C:/Users/yourname/Dropbox/Apps/Overleaf/<project-name>"
```

All scripts read raw data from `gdrive_project_path` and push outputs to `dropbox_project_path`. The project's shared scripts use these variables — never hardcoded paths.

Document the expected variables and provide a copy-paste template in both `CLAUDE.md` and `COAUTHOR_GUIDE.md`.

## Git Workflow

- **`main` stays clean.** All contributors work on named branches; merge into `main` via PRs only — no direct pushes to `main`.
- **Branch naming:** `{topic}` or `{initials}/{topic}` (e.g., `weight-recovery`, `fg/cleaning-fixes`).
- **PRs:** Open a PR when a chunk of work is ready. A collaborator reviews (or approves quickly for low-stakes changes). The audit trail and clean `main` are the value, not the formality.
- **Push at session end.** Don't leave unpushed commits locally overnight — collaborators may need your branch state.
- **Commit conventions** are the same as solo work — follow `rules/rules.md`.

## renv Discipline

- Run `renv::restore()` at the start of every analysis session.
- If you install or update a package: `renv::snapshot()` → commit `renv.lock` → push → all collaborators run `renv::restore()`.
- Never `install.packages()` without following through with `renv::snapshot()` and committing the lock file.
- When merging branches that both touched `renv.lock`, resolve the conflict carefully — keep the union of packages, not one author's snapshot over the other's.

## COAUTHOR_GUIDE.md

Every project with co-authors must have a `COAUTHOR_GUIDE.md` at the **project root** — a brief, plain-language document for someone who has never seen the project before. Create it when adding the first co-author (Step 8 of `new_project.md`). **Update it whenever co-author conventions change for the project.**

Each section should open with 1–2 sentences explaining the purpose of the tool or convention to someone who has never encountered it — write for a PhD student on their first day, not an experienced developer.

Required sections:
1. **Required tools** — Git, R (plus any editor), GitHub account, Google Drive (or Nextcloud), Dropbox; optional GitHub Desktop. Do NOT list a specific editor as required. Mention Nextcloud as an alternative if applicable (e.g., university-provided).
2. **Where files live** — the three-location model as one integrated section with subsections:
   - *Local folder — code (git-tracked):* clone into a local (non-cloud-synced) folder; explain why cloud + git conflict; show the four top-level folders (`analysis/`, `claude/`, `literature/`, optionally `programming/`); include the folder tree with numbered pipeline stages and "generated" labels for gitignored folders; list key root files (`CLAUDE.md`, `renv.lock`, `config_local.R`, `Claude_suggestions.R`); explain how to run the pipeline (entry point script, stage independence — later stages can run if earlier outputs exist); clone instructions (SSH + HTTPS)
   - *Google Drive (or Nextcloud) — shared data and materials:* folder template (`data/`, `materials/`, `literature/`); note that scripts find data via `config_local.R`
   - *Dropbox — Overleaf sync:* who owns the Overleaf connection; how `sync_to_dropbox()` works; fallback (manual upload via Overleaf web); Overleaf folder structure with path convention (`\input{study_1/main/tables/...}`)
   - *Summary table:* Location × What × How shared
3. **Git workflow** — branches, PRs, no direct pushes to `main`; include a "New to Git?" note recommending Claude Code as the easiest path, then GitHub Skills and GitHub Desktop as alternatives, plus the 4 daily commands
4. **Package management** — renv for R projects (restore before sessions, snapshot+commit after installs); uv for Python projects (equivalent discipline)
5. **Claude_suggestions.R** — frame as primary author's personal AI workflow; co-author can ignore; if they want similar, create own file
6. **Machine-specific setup (`config_local.R`)** — copy-paste template with paths for Google Drive/Nextcloud and Dropbox; note it is gitignored
7. **Verify your setup** — `check_setup.R` (or equivalent) verifies git config, renv status, cloud paths, folder location; fix any failures before proceeding
8. **Questions?** — point to `CLAUDE.md`, `claude/OPEN_ISSUES.md`, and creator contact details

## Author Profiles

Every project should have a `claude/about-team.md` — one section per author, each tagged with their git email. Loaded at session start (the session start protocol (`commands/startup.md`)) so Claude knows who it's working with and calibrates accordingly.

**Primary author setup (at project init):** copy `~/.claude/about-me.md` into `claude/about-team.md` as the first section. This is part of Step 5 of `new_project.md`.

**Co-author onboarding:** kindly ask the co-author to add their own section to `claude/about-team.md` before their first session. Explain the reason: having a short profile allows Claude to tailor its answers to their specific role in the project and their stage in their research career — a PhD student gets more explanation of methodology choices, a senior collaborator gets more terse and technical responses. Frame it as a one-time, low-effort investment that makes every Claude interaction more useful for them personally.

Minimum content to ask for: git email, academic background and field, career stage, role in this project, and any preferences for how Claude should communicate with them (e.g. how much explanation they want, preferred language).

## Convention Enforcement in Project CLAUDE.md

The project `CLAUDE.md` must contain explicit enforcement instructions so that Claude reminds all users — including co-authors — when they are about to violate a shared convention. This is necessary because a co-author's Claude session loads the project `CLAUDE.md` but not the primary author's `~/.claude/rules/`.

**General principle:** any convention that should govern a co-author's Claude session must **also** live in the project `CLAUDE.md`. The `~/.claude/` files are machine-local and invisible to the co-author's Claude. The global files are the canonical templates; the project file is what both sessions actually load.

**How to decide what to copy:** this is a one-time judgment call made explicit at co-author onboarding (Step 8 of `new_project.md`). The primary author reviews the global conventions and copies the Claude-instruction parts of any convention that should be enforced in all authors' sessions. Doing this once at onboarding — not ad hoc later — is what keeps the project `CLAUDE.md` complete and the co-author's Claude well-informed.

Add the following blocks to the project `CLAUDE.md` whenever co-authors are working in the project:

```
## Decision Documentation

When an analytical or methodology decision requires weighing multiple options, create a discussion file in `claude/` before resolving it — lay out the options, tradeoffs, and implications, then decide. Use descriptive filenames (e.g. `methodology_bayesian_updating.md`, `data_cleaning_outliers.md`).

When a problem is resolved mid-session (a specification choice, a data cleaning decision, a modelling approach), document it in a discussion file even if the resolution was quick: what the issue was, what was decided, and why.

Before closing any session where a significant decision was made, confirm a discussion file exists. If not, create one before wrapping up.

## Session Start

At the start of every session:
1. Run `git config user.email` to identify the active author.
2. Read `claude/about-team.md` and load the section matching that email as context — this calibrates communication to the author's background and role.
3. Read `claude/next_steps_[initials].md` for the matching author (see `Session file:` field in their profile) to surface where they left off.

If no matching profile is found in `about-team.md`, proceed normally and suggest the author adds their profile (see `COAUTHOR_GUIDE.md` Section 7).

### Convention Enforcement

Flag immediately when any user does the following:
- **renv:** runs `install.packages()` without following with `renv::snapshot()` + committing `renv.lock`
- **Git:** pushes or commits directly to `main` instead of a named branch + PR
- **Staging:** edits `Claude_suggestions.R` directly (it is a staging file, not a content script)
```
