Explain, in plain terms, what the user needs to understand: the thing named here
($ARGUMENTS), or, if nothing is named, what was just discussed or just done.

**This is a re-explanation, not new work.** Do not investigate, open new files or run anything.
If an honest answer needs a fact you do not have, name the missing fact and stop: an
explanation that fills a gap with a plausible guess is worse than the confusion it replaces.

## Plain about the machine, exact about the field

- **Unpack** programming, software and tool vocabulary: commands, file names, error messages,
  how Claude Code works.
- **Do not simplify** the vocabulary of the user's own field (their profile names it). There the
  term is the information.

## Start with what is at stake

Open with the real problem: what goes wrong, for the user, in their project. Then what was done
about it. Make the consequence concrete ("the table would then count each company twice")
rather than abstract ("duplicate keys degrade the merge").

## Answer the gap, not a template

Ask what the user is missing that would make this make sense, and answer that. Often it is one
of these; covering one is a normal answer:

- what the thing is;
- why it exists, or how it got this way;
- what went wrong, and why (if the cause is unknown, say so);
- what was done and what changed (the substance, not a file list);
- the options and what each costs (only if something is undecided);
- what it does NOT cover: what is unchecked or left undone.

## Discipline

- Length follows the question. A small confusion gets a short answer.
- Name a file only if the user would open it.
- One analogy at most, and only if it does work.
- Say what something IS before what you think it MEANS.
- No new claims: everything said must already have happened or been read in this session.

When the object is the work just done, this recap cannot say whether that work was good: it
comes from the session that did it. For that, `/what-slipped` sends the work to a fresh reviewer.
