# Research Integrity

**Load when:** producing, checking or reporting any number, dataset or analysis that may enter a paper, talk, grant proposal, pre-registration or replication package; or when an API, scraper or LLM collects, codes or classifies a study's data.
**Skip when:** throwaway exploration that will never be shared or cited; pure formatting or prose.

Load alongside `SKILL.md`.

## The one rule

**A number that goes into a paper, talk or proposal must be reproducible from a script and
checked.** Exploratory code can be quick and loose. But the moment a number enters something other
people read, it is publication-bound, even if it came from a quick first look. A pilot may make a
modest claim, but the claim must still be correct: a feasibility pilot with a wrong number proves
the opposite of feasibility.

Why this needs a rule with Claude: Claude makes it effortless to produce one more specification,
one more table, one more summary figure. Each is plausible on its own, and none is checked unless
checking is part of the routine.

---

## Always on, even for exploratory work

1. **No silent fallbacks.** No `try`/`except` (or `tryCatch`) that returns a default value when a
   step fails, and no switch to synthetic or cached data without a loud message. Assert that the
   real source was used (rows read > 0, the API returned an ID). Why: this is the only way a run
   that "succeeded" can produce a fake number.
2. **Every number Claude states carries its source:** the script and output file it came from, or
   `[unverified]` when it is from memory or an estimate. An untagged number is not to be trusted.
3. **Every result-affecting choice is visible in the main script.** Sample restrictions,
   thresholds, seeds, model options are set at the top of the script that runs the analysis (or in
   one config block), never as hidden defaults inside helper functions. Why: anyone, including you
   in a year, can then see every degree of freedom in one place.
4. **Raw data is read-only.** Scripts read from the raw-data folder and write elsewhere.
5. **Seeds are set and recorded; package versions are locked** (`renv.lock`, `uv.lock`).

## Keep collection and analysis apart

When data come from an API, a scraper or an LLM:

- **Collection** writes every raw response to disk once and never overwrites it, together with the
  date, the exact source version (for an LLM: model name and version string) and any seed.
- **Analysis** reads only those saved files. **Test: it must run with the internet switched off.**

Why: providers change models and endpoints without notice. If the analysis needs a live call, the
number can never be reproduced, and nobody can tell whether it changed because the code changed or
because the provider did.

## Before a number goes out: the check

Each step leaves evidence that someone else could look at.

1. **The plan predates the result** (for confirmatory claims). Hypothesis, exact metric,
   exclusions and pass/fail threshold are written down and committed before the run, so the git
   history shows the order. A "pass" means "at least the number written down beforehand". (Writing
   the plan: the `analysis-plan` skill.)
2. **A clean rerun reproduces it.** A fresh R or Python process runs the main script top to bottom
   from raw data with the locked packages and gives the same number. Record the script, the commit,
   the data file and the seed beside the number.
3. **Every sample restriction is a runnable condition, not a name.** "Clean responses only",
   "the usable sample" or "excluding outliers" are labels; a filter expression is a definition.
   Record the expression and the resulting n beside every number that rests on a subset.

   ```
   # WRONG
   "Clean responses only (n = 640): mean WTP 4.21"
   # RIGHT
   attention_check == 1 & duration_sec >= 120 & !is.na(wtp)   ->  n = 640, mean WTP 4.21
   ```

   If you cannot write the condition down, you have found the problem: settle it before the number
   is quoted again.
4. **Tables are generated by script and recounted against the data**, all rows, not only the ones
   that look wrong (`SKILL.md` § Verifying a result).
5. **A placebo fails.** Wherever the pipeline classifies, scores or tests, run it once on something
   that must not pass: shuffled labels, a placebo treatment date, a fake cutoff. If the placebo
   also "works", the pipeline is leaking the answer.
6. **An independent check agrees.** Either a second implementation (below), or a fresh session
   (a new conversation, or a subagent) that reproduces the number from the plan and the raw data
   without seeing the original code.
   - Withhold everything the number is *computed from*: the code, intermediate files, your summary
     of the logic. Hand over the plumbing: where the raw data is, the file layout, an API's quirks.
     Test for each piece: *could knowing this let the checker reproduce my mistake?* If yes,
     withhold it.
   - **Two checks that read the same intermediate file are one check.** If both start from the same
     cleaned dataset, a cleaning error reproduces perfectly. Vary the shared step, or compare against
     a value written down before the run.
7. **The result survives the pre-specified robustness checks**, and the ones it fails are reported.
8. **The researcher runs it once.** You run the main script yourself, once, and look at the output.
   A result that only Claude has ever produced does not go out on Claude's word.

**Deviations from the plan** go into `analysis_plan_deviations.md` with the original plan, the
change and the reason, at the time they happen. A silent deviation is the thing pre-registration
exists to prevent.

## A second implementation in the other language

For deterministic steps whose output enters the paper (raw data to analysis dataset, scores and
payoffs, exclusion rules, the numbers in a table), **propose** a second implementation in the other
language (an R version of a Python step, or the reverse) plus a test that the two outputs are
identical, on a small hand-made example and on the real data. Why: two independent
implementations rarely make the same mistake, and it is much harder to hallucinate the same wrong
result twice in two languages.

- Only for deterministic steps. Live API or LLM calls give different answers each time, so
  "agreement" is undefined there.
- Propose, do not impose: time pressure is a legitimate reason to skip it, but record that it was
  skipped.

---

## When an LLM is part of the data

Applies when a language model is the study's subject, or codes, classifies or rates the data.

- **The working Claude session is never the coder of record.** Classes assigned in conversation
  are unreproducible and unvalidated, and the drift is gradual: Claude drafts a rule from counts,
  the researcher agrees in a minute, the rule gets applied, and nobody has looked at real cases.
  Use ordinary content analysis instead:
  1. A **codebook** before coding: definition, decision rule and real examples per class.
  2. **One deterministic classifier script** that writes a label file, tested on cases with known answers.
  3. **Blind human validation** by at least two coders on a stratified sample, with agreement reported.
  4. Claude's role is stated: it drafts codebook options and builds the tools; the write-up says so.

  A rule-based classifier errs by input pattern, not at random: it mislabels a whole combination of
  fields or none of it. So check at least one case of every distinct combination the rule reads,
  then add a random sample.
- **The prompt is the instrument.** Editing a prompt is rewording a questionnaire item: version
  every prompt, and treat a change after data collection has started as a change to the data.
  Check a revision **per condition, never pooled**: a change that improves the average while
  breaking one condition is differential measurement error across arms, and it biases the
  treatment contrast while the pooled quality number goes up. Write the expected answers to probe
  items from real model output, not from imagination, and check breakage with deterministic checks
  (did the format hold, did the label match), not with another model as judge.
- **Who is answering is part of the instrument.** A model asked to *play* ("you are Player 1"), to
  *advise* ("what should a person do?") and to *forecast* ("what will Player 1 do?") gives
  different answers, sometimes in a different order across games. Name the mode in the plan; if
  the design treats one as another, test the equivalence on a subset.
- **Models are not a random sample.** A handful of accessible models, several from one family, is
  a convenience set of near-copies. Count families, not versions. "Holds across our four models"
  means "not falsified on the models we ran", not "generalizes"; a spread across models describes
  those models, it does not estimate a population variance. The claim such a set supports well is
  existence: "at least one widely used model does X".
- **Record the exact model version and date** for every call; providers update models silently.
- **Circularity.** If a Claude-family model is the subject while Claude writes the analysis code,
  say so, and prefer a different model family for the tooling where possible.

## Disclosure

Most publishers now ask for a statement of how AI tools were used. Keep a short running note of
what Claude did in each project (coding, data cleaning, drafting, checking), so the statement is
accurate rather than reconstructed at submission. Check the target journal's policy.
